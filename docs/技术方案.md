## 1. Why：这套东西到底在干什么

先讲清原理，否则后面所有设计都成了玄学。

### 1.1 网关是怎么"拦住"你的

插上网线后，DHCP 会正常给你分配 IP，**链路层和网络层其实是通的**。网关在应用层做封锁，常见三种策略：

| 策略 | 表现 | 能否程序化 |
|---|---|---|
| **A. HTTP 302 重定向**（最常见） | 浏览器随便打开一个 http 网站，被跳到 `http://10.x.x.x/srun_portal_pc?ac_id=1&...` | ✅ 最容易 |
| **B. 白名单放行** | 只放行认证服务器 IP，其他全部丢包 | ✅ 可行，只是探测手法不同 |
| **C. 返回 200 + 提示页** | 不重定向，直接返回一段"请先认证"的 HTML | ✅ 可行 |

**关键认知：封锁只发生在 HTTP 层，且通常只劫持 HTTP（80 端口），不劫持 HTTPS（443）。**
因为 HTTPS 有证书校验，网关无法伪造合法证书做重定向——所以：
- 你打开 `https://www.baidu.com` 会**超时/证书报错**，而不是跳到认证页；
- 你打开 `http://www.baidu.com` 才会**被跳到认证页**。

这条认知直接决定了后面"探测是否已认证"该怎么做。

### 1.2 认证的完整时序

```
① 插网线 → DHCP 拿 IP（不需要认证）
        ↓
② 程序发 HTTP 探测请求（例如 http://connect.rom.miui.com/generate_204）
        ↓
   已认证？──返回 204 / 预期内容──→ 什么都不做，继续待机
        │
        └─未认证？──返回 302 重定向──→ 从 Location 头里解析出认证页 URL
                ↓
③ 解析 URL 里的动态参数（ac_id、wlan_user_ip、nas_ip…）
        ↓
④ 拉取认证页 HTML，按需请求 token / challenge 接口
        ↓
⑤ GET /eportal/?c=Portal&a=login 提交学号 + 密码（本校无加密，实测见协议分析）
        ↓
⑥ 解析返回 JSON：{"code":0,"msg":"success"} → 认证成功，网关放行该 IP
        ↓
⑦ 起一个定时器，每 N 秒探测一次，掉线自动重来 ②
```

这就是整个程序的全部逻辑，**没有黑魔法**。

### 1.3 为什么必须用 "HTTP 204 探测" 而不是 ping

| 探测方式 | 能否判断"已认证" | 说明 |
|---|---|---|
| `ping baidu.com` | ❌ **完全不行** | 网关不封 ICMP，未认证时 ping 照样通 |
| `curl https://baidu.com` | ❌ 不行 | HTTPS 不被劫持，超时是"网络不通"而非"未认证"，无法区分 |
| `curl http://generate_204` | ✅ **正确做法** | 已认证返回 `204`；未认证返回 `302` 或 200+HTML。语义清晰 |

这也是 Android / iOS / Windows 系统判断"是否需要登录 WiFi"用的同一套机制（Captive Portal Detection）。**我们复用它，等于免费拿到了一个标准答案。**

## 3. How：分层架构

设计原则：**探测、协议、配置、调度四者解耦**。这样学校换网关时，只需要新增一个协议适配器，其余代码零改动。

```
┌─────────────────────────────────────────────────┐
│  接入层  Entry                                   │
│  CLI 参数 · 托盘菜单 · 任务计划程序 · 系统服务    │
├─────────────────────────────────────────────────┤
│  调度层  Scheduler                               │
│  轮询定时器 · 指数退避 · 网络变化事件监听          │
├─────────────────────────────────────────────────┤
│  协议层  Portal Adapter（可插拔）                 │
│  ┌────────────┬────────────┬────────────────┐  │
│  │ Srun 深澜   │ DR.COM     │ Generic 通用表单 │  │
│  └────────────┴────────────┴────────────────┘  │
├─────────────────────────────────────────────────┤
│  探测层  Prober                                  │
│  204 探测 · 在线判定 · 网关可达性                 │
├─────────────────────────────────────────────────┤
│  基础层  Infra                                   │
│  HTTP Client · 配置加载 · DPAPI 加密 · 日志       │
└─────────────────────────────────────────────────┘
```

### 3.1 各层职责

| 层 | 职责 | 关键设计点 |
|---|---|---|
| 基础层 | HTTP 请求、配置读写、凭证加密、日志 | HTTP Client **禁止自动跟随重定向**，否则拿不到 `Location` 头里的参数 |
| 探测层 | 判断"现在需不需要认证" | 用 captive portal 标准探测 URL，同时准备 2～3 个备用 |
| 协议层 | 厂商差异隔离 | 统一接口 `Login(ctx, cred) error`，各厂商一个实现，用注册表模式按 URL 特征自动匹配 |
| 调度层 | 决定"什么时候探、失败怎么等" | 指数退避，避免狂刷登录接口被网关封 IP |
| 接入层 | 让"人"能用上 | 首版 CLI，稳定后加托盘 |

### 3.2 协议适配器的统一接口

这是整个设计的**核心抽象**，也是开源项目能不能被别人复用的关键：

```go
type Adapter interface {
    // 用重定向 URL + 页面内容判断能否处理这个网关
    Detect(portalURL string, body []byte) bool
    // 从重定向 URL 中提取动态参数
    Parse(portalURL string) (map[string]string, error)
    // 执行登录，返回是否成功
    Login(ctx context.Context, cred Credential, params map[string]string) error
}
```

`Detect()` 是灵魂——程序先请求一次随便的 http 网址，拿回跳转 URL，然后**依次问每个适配器"你能处理吗"**。谁认识就用谁。这样：

- 深澜的学校 ✅ 用 Srun 适配器
- 用 DR.COM 的学校 ✅ 自动走 DR.COM
- 小众网关 ✅ 用 Generic 适配器，靠配置文件里的字段映射硬吃
- 未来新网关 ✅ 提一个 PR 加个文件，不用改主流程

### 3.3 状态机

程序只有 4 个状态，逻辑极简：

```
        启动
         ↓
   ┌──→ [探测中] ──已认证──→ [待机] ──N秒后──→ [探测中]
   │        │
   │     未认证
   │        ↓
   │    [认证中] ──成功──→ [待机]
   │        │
   └──失败──┘（退避 5s → 10s → 30s → 60s，封顶）
```

## 4. 技术选型

### 4.1 语言对比

| 语言 | 分发体积 | 常驻内存 | 开发速度 | Windows 适配 | 结论 |
|---|---|---|---|---|---|
| **Go** | ~6 MB 单文件 | ~8 MB | 中 | 好（托盘/服务库成熟） | ✅ **推荐** |
| Python | PyInstaller 打包 15～25 MB，启动慢 | ~35 MB | 快 | 一般（打包坑多、易被误报毒） | △ 适合做 PoC，不适合做最终交付 |
| C# / .NET | 需 Runtime 或 AOT 单文件 ~15 MB | ~25 MB | 快 | **最好**（WinForms 托盘最省事） | △ 可行，但要拖 .NET 依赖 |
| Node / Electron | 100 MB+ | 100 MB+ | 快 | 一般 | ❌ 违背"不占资源"，直接排除 |
| AutoHotkey / BAT | 极小 | 极小 | 极快 | 差 | ❌ 只能应付最简单的明文表单，不可靠 |

### 4.2 推荐：Go

**为什么是 Go（而不是 Python / C#）：**

1. **单文件 exe，双击就跑** —— 直接命中"开箱即用"。同学不需要装任何运行时。
2. **常驻 8 MB 内存，空闲 CPU 0%** —— 直接命中"不占系统资源"。Electron 方案的 1/12。
3. **加密算法全在标准库** —— `crypto/hmac`、`crypto/md5`、`crypto/sha1` 开箱可用，深澜那套 HMAC-MD5 加密几行就能写。
4. **交叉编译发布简单** —— GitHub Actions 一键出 Release 二进制，开源项目的标准姿势。
5. **`golang.org/x/sys/windows`** 直接调 DPAPI 加密密码，无需额外依赖。

**代价**：比 Python 略难写，且需要手写加密逻辑。但换来的是分发和资源上的质变。

### 4.3 建议的落地路径（先快后稳）

> 这里有个务实考虑：**Go 写协议逆向的迭代速度不如 Python。**

| 阶段 | 用什么 | 目的 | 产出 |
|---|---|---|---|
| **M0 侦察** | ✅ **已完成**（逆向网关前端 JS，非抓包） | 摸清协议、确认无加密、无验证码 | `docs/协议分析.md` |
| **M1 验证** | **Python** PoC（代码已写好） | 真机验证"到底能不能连上" | `poc/drcom_login.py` 跑通 |
| **M2 产品化** | **Go** | 正式项目：单文件 + 托盘 + 自启 + 加密 | v0.1.0 Release |
| **M3 打磨** | Go | 适配器插件化、多语言 README、CI 发布 | v1.0.0 开源 |

**为什么要绕一趟 Python？** 因为 M0/M1 阶段你是在猜协议，改一次编译一次实在太慢。Python 可以边改边跑，把协议摸清后再用 Go 一次写对。**这是省时间，不是多此一举。**

## 5. 配置文件设计（开箱即用的核心）

目标：**用户只需要改 3 行。**

```yaml
# config.yaml —— 从 config.example.yaml 复制而来（完整模板见仓库根目录）
account:
  username: "2023001234"   # ← 改这里
  isp: "campus"            # ← 改这里（telecom/cmcc/unicom/campus）

portal:
  url: ""                  # 留空 = 自动探测
  type: "auto"             # auto / drcom / generic
  host: "172.16.8.22"      # Dr.COM 网关
  port: 801                # 注意是 801，不是 80
  login_method: 1          # Portal 协议模式
  js_version: "3.3.3"
  account_prefix: ",0,"    # 账号前缀；认证失败时改成 "" 再试

behavior:
  check_interval: 30       # 探测间隔（秒）
  reconnect_delay: 5       # 重试延迟（秒）
  backoff_max: 60          # 指数退避封顶
  max_fail_before_alert: 5 # 连续失败几次后停止重试（防触发验证码风控）
  auto_start: true         # 是否注册开机自启
```

**设计要点：**

- `type: auto` 是默认值 → 用户**不需要知道**自己学校用什么网关。这是"开箱即用"的关键。
- 所有字段都有合理默认值 → 用户**只需要填账号密码**。
- `field_mapping` 只对 Generic 类型生效 → 主流网关用户完全不用碰。

### 5.1 凭证安全

| 方案 | 安全性 | 复杂度 | 采用 |
|---|---|---|---|
| 明文写在 config.yaml | ❌ 极差，截图/分享/提交 git 就泄露 | 最低 | ❌ |
| **Windows DPAPI 加密** | ✅ 绑定当前 Windows 用户，换机/换用户无法解密 | 低（系统 API） | ✅ **推荐** |
| AES + 硬编码密钥 | △ 密钥在二进制里，可被逆向 | 中 | ❌ 自欺欺人 |
| 系统凭据管理器 | ✅ 系统托管 | 中 | △ 可选 |

**推荐做法：**
1. 首次运行时让用户输入密码；
2. 用 DPAPI（`CryptProtectData`）加密后存到 `%APPDATA%\auto-connect\cred.dat`；
3. `config.yaml` 里**只存用户名，不存密码**；
4. `.gitignore` 里排除 `config.yaml`、`cred.dat`、`*.log`。

> ⚠️ 开源项目最容易挨骂的点就是"作者把真实账号密码提交上去了"。这个必须从第一天就做对。

## 6. 开机自启方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 注册表 `Run` 键 | 简单，代码 5 行；**兼容性最好，几乎不会被策略挡住** | 无延迟控制，可能早于网络就绪；易被杀软关注 | △ 降级备选 |
| **任务计划程序** | 可设**延迟启动**（避开网络初始化）、可设"网络可用时触发"、崩溃自动重启 | 需要写 XML；**部分环境被组策略/安全软件挡住** | ✅ **首选** |
| Windows 服务 | 完全无感 | 调试麻烦、需管理员权限、GUI 交互受限 | △ 进阶可选 |

**最终实现：两条通道，自动切换。**

```
注册开机自启
   ↓
① 任务计划程序（首选）
   XML 写临时文件 → schtasks /Create /XML
   ↓ 成功
   顺手清掉可能残留的注册表项，避免开机启动两次
   ↓ 失败（策略拦截 / XML 被拒 / 权限不足）
② 注册表 HKCU\...\Run（降级）
   reg add ... /d "\"<exe路径>\" daemon --hidden --delay 30"
   ↓
   程序自己用 --delay 实现延迟：每 2 秒探一次默认路由，
   网卡一拿到 IP 就立刻开工（比死等 30 秒体验好）
```

任务计划用来兜住"延迟 + 网络就绪 + 崩溃重启"这些能力；
注册表用来兜住"任务计划被禁用"的极端环境。
菜单和 `status` 会显示**实际生效的是哪一种**。

> 为什么必须修编码：`schtasks` / `reg` 在中文 Windows 上输出 GBK，
> 如果按 UTF-8 硬读，报错会变成一串 `????`，真正的失败原因直接丢失
> —— 用户只看到 `exit status 1`，无从排查。
> 现用 `kernel32!MultiByteToWideChar(CP_ACP)` 解码（零第三方依赖）。

## 7. 风险与对策

| # | 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|---|
| 1 | ~~认证参数加密~~ | — | — | ✅ **已排除**：`enMd5 = 0`、`enHttps = 0`，密码明文提交 |
| 2 | **密码输错会触发验证码** | 中 | 中 | 不做无限重试：连续失败 5 次即停止并提示用户检查密码（避免触发风控） |
| 3 | 动态参数变化（`wlan_user_ip` 等） | 高 | 中 | 本机 IP 用 UDP connect 自动探测；其余从 302 重定向 URL 实时解析，**不硬编码** |
| 4 | 学校升级网关打破脚本 | 中 | 中 | 适配器可插拔 + 协议版本号 + 清晰的失败日志 |
| 5 | 狂刷登录接口被网关封 IP | 中 | 中 | 指数退避，最小间隔 5s，封顶 60s |
| 6 | 杀软误报（打包 exe 常见） | 中 | 中 | Go 静态编译 + 开源 + 不混淆；README 说明 |
| 7 | 密码泄露 | 中 | **高** | DPAPI 加密 + .gitignore + 启动时不打印密码 |
| 8 | 违反学校网络使用规定 | 中 | 中 | README 加免责声明，说明仅用于个人设备便利登录，不绕过计费/限速 |

> **关于风险 8 的诚实说明**：自动化登录本身不改变认证强度（还是你的学号密码），只是省去手动点击。但如果学校明确禁止脚本登录，需自行评估。开源时建议在 README 顶部写明用途边界。

### 已经可以确定的 Go 侧实现细节

```go
// 登录请求（PoC 已实测通过的形态）
url := fmt.Sprintf(
    "http://%s:%d/eportal/?c=Portal&a=login&callback=dr%d&login_method=1"+
        "&user_account=%s&user_password=%s"+
        "&wlan_user_ip=%s&wlan_user_ipv6=&wlan_user_mac=000000000000"+
        "&wlan_ac_ip=&wlan_ac_name=&jsVersion=3.3.3&v=%d",
    host, 801, rand.Intn(9000)+1000, account, password, localIP, rand.Intn(9900)+100)
// 注意：account 与 password 都要 url.QueryEscape
```

**失败码处理**（照 `协议分析.md` §3.6 的表）：
- `ret_code=1`（账号或密码错）→ **停止高频重试**，提示用户核对密码
- `ret_code=2`（IP 已在线）→ 视为正常，不报错
- 其余 → 指数退避后重试
