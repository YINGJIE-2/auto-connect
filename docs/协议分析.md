## 2. 认证流程

```
① 插网线 → DHCP 分配 IP（如 10.200.11.126）—— 无需认证
        ↓
② 发 HTTP 探测：GET http://connect.rom.miui.com/generate_204
        ↓
   已认证? ── 204 ──────→ 什么都不做
        │
        └── 302 重定向 ──→ 从 Location 抠出 wlanuserip / wlanacname / wlanacip
                ↓
③ GET http://172.16.8.22:801/eportal/?c=Portal&a=login&...  （JSONP）
        ↓
④ 返回 drXXXX({"result":"1", ...}) → 认证成功，网关放行
```

**实测验证**：未认证时访问 `http://connect.rom.miui.com/generate_204` 被网关 302 拦截；已认证时返回 `204`。已联网状态下 `msftconnecttest.com` 返回 `200`。

## 3. 登录请求完整规格 ★核心

### 3.1 请求

```
GET  http://172.16.8.22:801/eportal/?c=Portal&a=login&callback=dr<随机4位>&login_method=1
     &user_account=<账号>
     &user_password=<密码明文>
     &wlan_user_ip=<本机内网IP>
     &wlan_user_ipv6=
     &wlan_user_mac=000000000000
     &wlan_ac_ip=
     &wlan_ac_name=
     &jsVersion=3.3.3
     &v=<随机数>
```

| 项 | 值 | 说明 |
|---|---|---|
| 方法 | **GET** | 通过 JSONP 变相实现（`util._jsonp` 用 `<script>` 标签发请求） |
| 端口 | **801** | 不是 80。`page.eportal = hostname + ':801/eportal/'` |
| 路径 | `/eportal/` | |
| 参数 | `c=Portal`、`a=login` | 动作标识 |
| 编码 | UTF-8 URL 编码，响应按 **gb18030** 解码 | |

**证据**（`a41.js` 第 119 行）：
```js
eportal: window.location.protocol + '//' + window.location.hostname + ':801/eportal/',
```
**证据**（`a42.js` 的 `portal_login`）：
```js
var url = page.loginMethod == 0 ? page.path + 'login' : page.eportal + '?c=Portal&a=login';
dr._jsonp(url, data, ...)
```

### 3.2 参数表

| 参数 | 取值 | 来源 |
|---|---|---|
| `c` | `Portal` | 固定 |
| `a` | `login` | 固定 |
| `callback` | `dr` + 随机数字 | JSONP 回调名 |
| `login_method` | `1` | `getLoginMethod()` 计算得出，见 §3.4 |
| `user_account` | **`,0,` + 学号 + 运营商后缀** | `login.prefixAccount` |
| `user_password` | **密码明文，无任何加密** | `enMd5 = 0` |
| `wlan_user_ip` | 本机内网 IP（本次实测 `10.200.11.126`） | `term.ip` |
| `wlan_user_ipv6` | 空 | 未启用 IPv6 |
| `wlan_user_mac` | `000000000000` 也可 | 该校区页面取不到 MAC，实测填全零可用 |
| `wlan_ac_ip` | 空 | 未在重定向参数中提供 |
| `wlan_ac_name` | 空 | 同上 |
| `jsVersion` | `3.3.3` | `a41.js` |
| `v` | 随机数 | 防缓存 |

**证据**（`a42.js` 的 `login.init` / `login.login` / `login_portal`）：
```js
this.accountPrefix = accountPrefix == 1 ? (term.type != 2 ? ',0,' : ',1,') : "";
this.prefixAccount = this.accountPrefix + this.form.DDDDD.value + this.tempAccountSuffix;
...
'user_account': this.prefixAccount,
'user_password': this.form.upass.value,
```

### 3.3 密码加密：**无**

`a41.js` 第 38 行明确写着：
```js
var enMd5 = 0;   // 是否需要MD5(0-不需要；1-需要)
```
另有 `var enHttps = 0; // 是否需要Https`。**so 密码明文走 GET 参数，不需要写任何加密算法。** 这也是为什么这个项目的实现难度比深澜网关低一个数量级。

### 3.4 为什么是 `login_method=1`

配置文件 `http://172.16.8.22:801/eportal/extern/WZXY/config.js` 中 `pageSetting = 2`（按 IP 段匹配），实际规则：

```
ipPageAry[0] = 默认模版|0.0.0.0|255.255.255.255|||1|0|          ← 审核标记=1，认证方式=0
ipPageAry[1] = WZXY   |0.0.0.0|255.255.255.255|||0|1|admin      ← 审核标记=0，跳过
ipPageAry[2] = WZXY-new|0.0.0.0|255.255.255.255|||1|1|admin     ← 命中！
```
字段顺序：`名称|起始IP|结束IP|虚拟商号|重定向地址|审核标记|认证方式|操作员`

`getMatchPage()` 遍历时要求 **`option_array[5] == '1'`（审核标记）**，只有 `[0]` 和 `[2]` 满足，且 `[2]` 后命中即 break（`[0]` 从 i=1 开始遍历）。所以：

- 命中 `ipPageAry[2]`（页面模板名 `WZXY-new`）
- `getLoginMethod()` 取 `paraArr[8-2] = paraArr[6]` = **`1`**
- `login_method = 1` → 走 `case 1: login_portal()` → **Portal 协议模式**

### 3.5 运营商后缀 ★易错点

登录页 `<select name="ISP_select">` 的实际取值（**来自真实页面 `ip/2/pc.js`**）：

```html
<option value="-1">请选择运营商</option>
<option value="@telecom">中国电信</option>
<option value="@cmcc">中国移动</option>
<option value="@unicom">中国联通</option>
<option value="">校园内网</option>
```

| 界面选项 | 后缀 | 最终账号（假设学号 2023001234） |
|---|---|---|
| 中国电信 | `@telecom` | `,0,2023001234@telecom` |
| 中国移动 | `@cmcc` | `,0,2023001234@cmcc` |
| 中国联通 | `@unicom` | `,0,2023001234@unicom` |
| 校园内网 | *(空)* | `,0,2023001234` |

**机制**：`loginMethod != 0`，所以 `setISP()` 走 else 分支 ——
```js
if (page.loginMethod == 0 && enableR3 == 1) { document.f0.R3.value = value; }
else { me.tempAccountSuffix = value; }     // ← 我们走这条，下拉框的值直接拼到账号后面
```

> **别踩的坑**：`a41.js` 里另有一段 `carrier` JSON（`@xyw/@dx/@lt`）。那是**全局默认值**，本校区已在页面模板里覆盖成了 `@telecom/@cmcc/@unicom/空`。以**页面模板**为准。

### 3.6 响应判定

返回 JSONP：`dr1234({"result":"0","msg":"QUM5OTk=","ret_code":2})`

解析方式：剥掉 `drXXXX(` 和 `)`，再 `json.loads`。

| 字段 | 含义 |
|---|---|
| `result` | `1` 或 `"ok"` = 成功；`0` = 失败 |
| `ret_code` | 失败原因码，见下表 |
| `msg` | **Base64 编码**的详情串 |

#### ret_code 对照表（逐条抄自 `a42.js` 的 `error.portal_login_err`）

| ret_code | 含义 | 程序该怎么处理 |
|---|---|---|
| 1 | 账号或密码不对，请重新输入 | ⚠️ **停止重试**，提示用户检查密码（继续试会触发验证码） |
| **2** | **终端IP已经在线** | ✅ 视为"已在线"，正常（我们的首次实测就返回这个） |
| 3 | 系统繁忙，请稍后再试 | 退避后重试 |
| 4 | 发生未知错误 | 退避后重试 |
| 5 / 6 | REQ_CHALLENGE 失败/超时 | 退避后重试 |
| 7 | Radius 认证失败 | 停止，提示用户 |
| 8 | Radius 认证超时 | 退避后重试 |
| 9 / 10 | Radius 下线失败/超时 | 退避后重试 |
| 11 | 发生其他错误 | 退避后重试 |
| 998 | Portal 协议参数不全 | ❌ **代码 bug**，检查参数拼装 |

> **实测记录（2026-10-10）**：在线状态下用 `user_account=,0,2023001234@cmcc` 提交，
> 返回 `{"result":"0","msg":"QUM5OTk=","ret_code":2}` → `msg` 解 Base64 得 `AC999`，
> `ret_code=2` = 终端IP已经在线。**这说明请求格式被服务端接受了**，仅因已有会话而拒绝。

#### `msg` 字段：RADIUS/LDAP 透传的错误原文（同样是 Base64）

`ret_code=1` 时服务端会把后端（RADIUS 或 LDAP）的原文塞进 `msg`。实测遇到两种：

| msg（Base64 解开后） | 出现的账号形态 | 真实含义 |
|---|---|---|
| `AC999` | 任意（已在线） | 伴随 `ret_code=2`，非错误 |
| `userid error2` | `学号@cmcc` | **账号或密码错误**（走 RADIUS 通道） |
| `ldap auth error` | 纯 `学号` | **账号或密码错误**（走 LDAP 通道） |

**官方释义（已交叉验证）**：
- Dr.COM 官方错误码表：`userid error2` = 「帐号或密码错误验证失败!!!」
- 广东药科大学现代教育技术中心公告：`userid error2` = 「认证账号的密码错误」
- 广东东软学院故障手册：`ldap auth error` = 「输入账号密码错误」

> ⚠️ **这两个错误不能区分「账号错」还是「密码错」** —— LDAP 对两种情况返回同一个错误。
> 程序遇到 `ret_code=1` 时应把它统一当作"凭据错误"处理：停止高频重试并提示用户核对密码。

#### 关于 `,0,` 前缀的修正

实测发现 **`,0,` 前缀对结果毫无影响** —— 加与不加，服务端返回完全相同的错误。
虽然 `a41.js` 里 `accountPrefix = 1`，但本校区实际不生效（或服务端会剥离）。
**最终决定：不发送前缀**，`user_account` 直接用 `学号` 或 `学号@cmcc`。

#### 关于运营商后缀

带 `@cmcc` 和不带后缀**都进入了凭据校验环节**（分别报 RADIUS/LDAP 错误），
说明两种形态都被服务端当作**合法账号**处理 —— 卡住的是密码，不是账号格式。
程序策略：先试 `学号@cmcc`（页面下拉框的值），失败再试纯 `学号`。


### 3.7 注销接口

```
GET http://172.16.8.22:801/eportal/?c=Portal&a=logout&login_method=1
    &user_account=drcom&user_password=123     ← 占位串，随便填但必须非空
    &ac_logout=1&register_mode=1
    &wlan_user_ip=<本机IP>&wlan_user_ipv6=&wlan_vlan_id=0
    &wlan_user_mac=<本机MAC>&wlan_ac_ip=&wlan_ac_name=&jsVersion=3.3.3
                                                              → {"result":"0","msg":"注销失败"}
```

**实测结论：本环境下注销接口不可用**（三种变体全部失败）：
- `wlan_user_mac` 用真实 MAC（`a1b2c3d4e5f6`）和全零都失败
- `?c=ACSetting&a=Logout&ver=1.0`（80 端口老接口）返回 404
- `?c=Portal&a=online_list` 返回「在线数据为空」——**Radius 里查不到以本机 IP/MAC 索引的在线会话**

推测原因：会话可能是「无感知 / MAC 认证」建立，或 `wlan_ac_name` 为空导致 Radius 匹配不上。
**对本项目无影响**——正式程序只需要「登录」和「探测」，完全不需要注销。

另可参考：`?c=Portal&a=unbind_mac`（解绑 MAC，需传真实 `user_account`，页面里 type=1 时会连带注销）。

## 4. 验证码机制

**结论：正常流程下不会遇到验证码，可以完全忽略。**

证据（真实页面 `ip/2/pc.js`）：
```html
<input class="edit_lobo_cell captcha" type="text" name="captcha" ... style="display: none; ...">
```
验证码输入框 **默认 `display: none`**，只有服务端在返回中带出验证码要求时，页面 JS 才会把它显示出来。

对应的逻辑分支（`a42.js` 的 `ee()`）：
```js
// 如果启用了验证码，则先检查验证码
if ($('input[name=captcha]')[0] && $('input[name=captcha]')[0]...)
```

**对我们的影响**：
- ✅ 密码正确 → 服务端不要求验证码 → 程序自动登录可行
- ⚠️ 密码写错 → 服务端要求验证码 → 程序会陷入"一直失败"，但**不会误判成功**

**工程对策**：如果连续认证失败 N 次，程序**停止重试并提示用户检查密码**，而不是死循环重试（否则可能触发风控）。这一条已写入设计方案。

## 6. M1 实测结论 —— **首次认证成功** ✅（2026-10-10 16:14）

实际生效的请求：

```
GET http://172.16.8.22:801/eportal/?c=Portal&a=login&callback=dr5766
    &login_method=1
    &user_account=2023001234@cmcc
    &user_password=<真实密码明文>
    &wlan_user_ip=10.200.11.126&wlan_user_ipv6=
    &wlan_user_mac=000000000000
    &wlan_ac_ip=&wlan_ac_name=
    &jsVersion=3.3.3&v=5180

→ dr5766({"result":"1","msg":"认证成功"})      耗时 146 ms
→ 复检：generate_204 = 204 ；baidu.com = 200 ；gitee.com = 301（真实跳转）
```

| # | 原待确认项 | 结论 |
|---|---|---|
| 1 | `,0,` 前缀是否必需 | ❌ **不需要**。加与不加服务端返回完全相同的错误 → 已从代码移除 |
| 2 | 运营商后缀取值 | ✅ **中国移动 = `@cmcc`**（页面下拉框的值），实测通过 |
| 3 | 密码错误的重试风控 | 未触发（首次即成功）。程序仍保守设上限：连续失败 5 次后降到 5 分钟一次 |
| 4 | 注销接口 | ⚠️ 对本机无效（见 §3.7），但**不影响本项目** |

### 踩到的坑（已写进产品需求）

**认证成功后网关放行有 1~2 秒延迟**，立即复检会误报"仍未联网"。
正式程序必须**重试复检**（PoC 已改为最多重试 4 次、每次间隔 1.5 秒）。
另外探测地址要有多个备选 —— 单个地址瞬时失败不代表未认证。

> 至此协议部分**已无任何不确定性**，可以进入 M2（Go 实现）。
